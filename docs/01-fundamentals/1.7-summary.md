# 1.7 小结：把这一章压缩成一页

::: tip 如果只记一句话
**Agent 是"模型在运行时决定下一步"的系统；它的成本花在上下文上，它的可靠性靠 harness。**
:::

## 1.7.2 十二道自测

先自己答，再点选项。做错不可怕，怕的是"以为自己会了"。

<QuizCard
  :index="1"
  question="下面哪种情况说明你写的确实是 Agent，而不是普通函数编排？"
  :options="[
    '代码里调用了大模型的 chat 接口',
    '使用了 Function Calling 来获取工具参数',
    '下一步调用哪个工具、调用几次，由模型在运行时决定',
    '有 while 循环'
  ]"
  :answer="2"
  explain="判断标准只有一条：<strong>控制流在谁手里</strong>。用了 Function Calling 但仍按固定顺序调用，本质是「用模型做参数抽取」的工作流。有循环也不一定是 Agent——固定次数的重试也是循环。"
/>

<QuizCard
  :index="2"
  question="推理模型决定调用工具时，`message.content` 为 null，真正的思考在哪？"
  :options="[
    '在 message.thought 字段',
    '在 message.reasoning_content 字段',
    '不会返回，需要重新请求一次',
    '在 tool_calls 的 arguments 里'
  ]"
  :answer="1"
  explain="DeepSeek、GLM、Qwen 等推理模型把思维链放在 <code>reasoning_content</code>（部分厂商用 <code>reasoning</code>）。这段内容<strong>照样计费</strong>，但不会出现在最终回答里。只读 content 的旧代码会白付这笔钱。"
/>

<QuizCard
  :index="3"
  question="MCP 在 2026-07-28 版规范里做了什么破坏性改动？"
  :options="[
    '把 JSON-RPC 换成了 gRPC',
    '移除了 protocol session 与 initialize 握手，核心改为无状态',
    '取消了 Tools 原语，只保留 Resources',
    '要求所有 Server 必须部署在云端'
  ]"
  :answer="1"
  explain="这一版把核心改成无状态，去掉了会话与初始化握手。所以读 MCP 文章要先看它引用的规范日期——2025 年写的连接逻辑可能已经不能用了。"
/>

<QuizCard
  :index="4"
  question="WebMCP 里注册页面工具的正确 API 是？"
  :options="[
    'navigator.modelContext.registerTool(...)',
    'window.mcp.register(...)',
    'document.modelContext.registerTool(...)',
    'navigator.serviceWorker.registerTool(...)'
  ]"
  :answer="2"
  explain="2026 年 7 月的草案把 API 从 <code>navigator</code> 迁到了 <code>document</code>，Chrome 150 已废弃旧写法。今年上半年的教程大量还在用 <code>navigator.modelContext</code>，属于过时信息。"
/>

<QuizCard
  :index="5"
  question="PEAS 里的 P（Performance）应该写成什么？"
  :options="[
    '用户满意度',
    '可观测的量化指标，例如缺陷发现率、误报率、平均响应时间',
    '模型的准确率',
    '代码行数'
  ]"
  :answer="1"
  explain="性能度量必须是<strong>可观测</strong>的指标。写不出 P，说明还没想清楚这个 Agent 优化什么——这类项目最后通常「演示惊艳、上线没人用」。"
/>

<QuizCard
  :index="6"
  question="把整个文档库都塞进上下文，最可能导致什么？"
  :options="[
    '模型一定回答得更准',
    '中段信息被忽略，关键信号被稀释（context rot）',
    'token 会更便宜',
    '响应更快'
  ]"
  :answer="1"
  explain="长上下文里中段内容最容易被忽略（lost in the middle），而且无关信息会稀释信号，业内称 context rot。正确做法是先检索、再摘要，只给当前步骤需要的片段。"
/>

<QuizCard
  :index="7"
  question="工具执行抛错时，最有利于 Agent 自我纠错的处理方式是？"
  :options="[
    '直接抛出异常终止进程',
    '捕获后打印日志，返回空字符串',
    '捕获后格式化成可读的错误说明，作为 Observation 回灌给模型',
    '自动重试三次，仍失败就静默跳过'
  ]"
  :answer="2"
  explain="自我修正不是模型变聪明了，而是你把错误信息喂给了它。<code>权限不足，请先执行 chmod +x</code> 比 <code>Error: failed</code> 有用得多。"
/>

<QuizCard
  :index="8"
  question="「每天定时汇总销售数据并发到群里」这个需求，最合适的实现是？"
  :options="[
    '自主 Agent，让它自己决定怎么汇总',
    '多智能体协作，分别负责取数、计算、发送',
    '固定工作流，步骤写死在代码里',
    '推理模型 + 长思维链'
  ]"
  :answer="2"
  explain="步骤固定、失败模式可枚举的任务，用工作流更可靠也更便宜。用 Agent 只会让你在出错时无法定位是哪一步的问题。"
/>

<QuizCard
  :index="9"
  question="关于推理模型的思考 token，下面哪句是对的？"
  :options="[
    '思考过程不计费',
    '思考过程计费，但通常不出现在最终回答里',
    '思考一定让结果更好，所以应该永远开到最大',
    '思考内容无法被程序读取'
  ]"
  :answer="1"
  explain="reasoning tokens 计入 completion，按输出价计费，且一般不出现在最终答案中。对「翻译一句话」这类任务，加思考预算只会更慢更贵、质量几乎不变。"
/>

<QuizCard
  :index="10"
  question="为什么「无进展检测」比「最大轮数」更重要？"
  :options="[
    '因为最大轮数会导致死循环',
    '因为最大轮数只能兜底，卡住的 Agent 会白白烧完所有轮次的钱',
    '因为 API 限制了轮数',
    '因为无进展检测能提高模型智商'
  ]"
  :answer="1"
  explain="最大轮数是最后一道保险，但它允许「空转 6 轮」这种浪费。无进展检测（工具名+参数+结果与上一轮相同）能在第 2 轮就止损。"
/>

<QuizCard
  :index="11"
  question="Agent 循环里，为什么「同一份系统提示」会被反复计费？"
  :options="[
    '因为厂商重复收费',
    '因为模型无状态，每次请求都要重新发送全部历史',
    '因为系统提示被缓存了',
    '因为工具调用要额外付费'
  ]"
  :answer="1"
  explain="LLM 不记得上一轮，history 必须每次重发，所以 prompt tokens 随轮数累积。省钱的唯一手段是命中 KV Cache——所以别在每轮开头改系统提示。"
/>

<QuizCard
  :index="12"
  question="什么时候才真的需要 A2A（多智能体横向协议）？"
  :options="[
    '任务比较复杂的时候',
    '想让效果更好的时候',
    '参与者属于不同组织，且不能共享内部上下文',
    '只要工具超过 5 个就需要'
  ]"
  :answer="2"
  explain="2026 年的共识是「单 Agent + 好工具」优先。多 Agent 意味着多份上下文、多次计费、误差累积。真正需要 A2A 的场景通常有一个硬特征：跨组织且上下文不能共享。"
/>

| 主题 | 建议读什么 | 注意 |
