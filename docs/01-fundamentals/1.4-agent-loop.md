# 1.4 Agent Loop：五步循环，以及它为什么越转越贵

::: tip 一句话结论
Agent Loop 本身只有十几行代码，**难的是"每一轮往上下文里放什么"**。
2026 年把这件事叫上下文工程，它的核心不是提示词技巧，而是预算管理。
:::

## 1.4.1 五个阶段，一次说清

<FigureBox
  src="/images/ch01/agent-loop.png"
  alt="Agent Loop：感知、思考（含规划与工具选择）、行动、观察、环境状态变化"
  caption="图 1.5 智能体与环境交互的基本循环。注意「思考」里还套了两个子步骤：规划与工具选择"

/>

| 阶段 | 发生了什么 | 对应代码 | 对应事件 |
| :--- | :--- | :--- | :--- |
| 感知 Perception | 把用户输入/上轮结果装进 messages | `messages.push(...)` | `round_start` |
| 思考 Thought | 模型推理：要不要调工具？调哪个？参数是什么？ | `llm.chat({ messages, tools })` | `reasoning` / `thought` |
| 行动 Action | 校验参数 → 执行函数 | `tool.execute(args)` | `tool_call` |
| 观察 Observation | 把结果序列化成文本，回灌上下文 | `messages.push({ role: 'tool' })` | `tool_result` |
| 判断 | 有 tool_calls 就继续，没有就结束 | `if (!res.tool_calls) return` | `final_answer` |

::: tip "思考"里其实有两件事
原书这张图把 Thought 拆成了 **Planning（规划）** 和 **Tool Selection（选工具）**。
在 2026 年的推理模型里，这两件事通常都发生在 `reasoning_content` 里，你看得见但不一定用得上；
而在非推理模型里，它们被压缩成一次前向计算，你完全看不见。
**看不见不等于没发生——它只是变成了不可观测的黑箱。**
:::

## 1.4.3 跟着看一遍：屏幕上会依次出现什么

这一节是写给第一次用的人的。实验台不是"一次性把答案吐出来"，而是**把内部过程放慢、一步一格地演给你看**。

### 建议的第一次操作

1. 点控制条最左边的**播放键**，让它自己走一遍，先建立整体印象；
2. 点**重播键**（第四个），这次点**暂停键**，再用**下一步键**一步一步往前走；
3. 每走一步，**先读最上面那句旁白**，再读下面卡片里的具体内容。

### 你会依次看到这 5 类卡片

| 屏幕上看到的 | 白话解释 | 它其实对应 |
| :--- | :--- | :--- |
| 🎯 **第 N 轮** | 模型又开始读一遍问题和历史 | 感知 Perception |
| 💭 **思考 · 心里话** | 模型在心里打草稿，你平时看不到的过程 | 思考（推理模型才有的思维链） |
| 🗣️ **思考 · 说出来** | 模型开口说了句话，例如"我先查一下天气" | 思考（可见的那部分） |
| 🔧 **行动 · 调用工具** | 模型点名要用某个工具，并给出参数 | 行动 Action |
| 📦 **观察 · 工具返回** | 工具真的跑完了，结果被塞回模型的记忆里 | 观察 Observation |
| ✅ **回答 · 整理成人话** | 模型认为信息够了，停止调用工具开始写答案 | 循环出口 |

::: warning 一个特别容易误会的地方
"模型说'我先查一下天气'"这句话**本身什么也没做**。
它只是表达了意图，真正去查要等下一步「行动 · 调用工具」。
这也是为什么你会觉得"思考完直接给答案"——中间那两张卡（行动、观察）才是真正干活的地方。
:::

### 实验台为了让你看清，专门做了这几件事

- **旁白条**：顶部一句话说明"现在这一步在做什么、为什么重要"，它跟着播放走；
- **当前这一步会被高亮**：其余卡片变淡，一眼能找到位置；
- **时间线自动跟随**：新的一步会自动滚进视野，不用手动往下拖；
- **工具调用有明确状态**：`⏳ 正在执行…` → `✓ 已返回 386ms`，不会一闪而过；
- **节奏按内容长度自适应**：一句话的步骤停留约 0.8 秒，一大段工具结果会停留更久（约 2–3 秒），不用手忙脚乱；
- **默认隐藏"记账"卡片**：token 数量对第一次阅读是噪音，想看可以在右上角打开「显示记账」；
- **步骤编号**：每张卡左上角有全局步骤号，配合旁白里的"第 3 / 12 步"。

### 怎么确认它是真实数据，不是编的

工具返回的卡片右上角会挂一个小标签，写明**数据来源和观测时间**，例如：

```text
观察 · 工具返回   386ms   [ Open-Meteo · 16:00 ]
```

- 有 `Open-Meteo · 16:00` → 真实接口，你可以拿手机天气 App 对这个时间和温度；
- 显示 `仿真数据` → 离线演示，**不代表真实天气**；
- 显示 `调用失败` → 接口挂了，模型会在下一轮读到错误并尝试重试。

::: warning 天气数据本身会有偏差
不同天气源对同一时刻的描述可能不同（"阴" / "多云" / "烟霾" 在边界上很模糊），
所以本项目的工具优先用 **Open-Meteo 的 WMO 标准代码**，并在返回里带上观测时间，
而不是丢一句没有出处的"今天晴"。
:::

## 1.4.4 一轮循环的真实成本

设：

- 系统提示 ≈ 160 tokens
- 两个工具的 JSON Schema ≈ 200 tokens
- 用户问题 ≈ 30 tokens

那么**每一次** LLM 请求都要重发全部历史：

| 轮次 | 发出去的 prompt 组成 | prompt tokens（约） |
| :--- | :--- | :--- |
| R1 | 系统 + 工具 + 问题 | 390 |
| R2 | 上一轮全部 + 工具调用意图 + 工具结果 | 700 |
| R3 | 再叠加一轮 | 1 050 |

结论：**同一份内容会被重复计费 N 次**。这不是实现缺陷，而是 LLM 无状态的必然结果——
模型不记得上一轮，只能你把历史再喂一遍。于是：

- 轮数越多，单轮越贵 → 所以要有**最大轮数**和**预算上限**
- 上下文越长，延迟越高 → 用户等待时间随轮数非线性上升
- 关键信息可能在长上下文里被"稀释" → 这就是 context rot

::: tip KV Cache 是唯一的省钱手段
相同前缀的请求可以命中缓存，只对新增部分计费。工程含义很直接：
**别在每轮开头改动系统提示**（比如往里插时间戳、随机 ID），否则缓存全废。
这条来自 Manus 团队的实践总结，2026 年已经是常识。
:::

## 1.4.5 上下文不是草稿纸，是预算

把上下文想象成一个**有固定容量的背包**，每走一步都要重新装一遍。下面这根条子可以拖着玩：把轮数拉到 10 以上，看窗口怎么被历史撑满。

<ContextBudget />

三种常见策略，通常组合使用：

| 策略 | 做法 | 适合 | 代价 |
| :--- | :--- | :--- | :--- |
| 滚动上下文 | 只留最近几轮，早期内容压成摘要 | 多轮执行、窗口有限 | 摘要会丢细节 |
| 任务状态对象 | 用结构化 JSON 记录目标/进度/约束 | 长任务、可恢复 | 需要额外维护 |
| 清空重启 | 把状态写成交接文档，重开上下文 | 超长任务 | 交接文档必须够完整 |

::: warning 一个真实的坑
向量记忆擅长"找相关内容"，但它**不能当真相源**。
如果第 12 步已经把 `status = waiting_for_approval` 写进状态，而检索又捞回第 4 步的"继续执行部署"，
模型很可能越过审批继续跑。所以任务状态一定要是**结构化对象**，不是一段被检索出来的文本。
:::

## 1.4.6 必须有的三个停止条件

没有停止条件的 Agent 就是一台烧钱机器：

1. **最大轮数**：本仓库默认 6 轮（`maxIterations`）
2. **预算上限**：累计 token 或金额超阈值就停
3. **无进展检测**：连续两轮工具返回相同/都是错误 → 停，并把错误交给人

```ts
for (let round = 1; round <= maxIterations; round++) {
  // ...请求模型、执行工具
  if (sessionTotalTokens > BUDGET) {
    yield { type: 'error', message: '预算超限，已停止' };
    return;
  }
}
```

::: details 为什么"无进展检测"比"最大轮数"更重要
最大轮数只能兜底，它会让一个卡住的 Agent 白白烧掉 6 轮的钱。
无进展检测能在第 2 轮就止损——判断依据可以很简单：工具名 + 参数 + 结果三者是否与上一轮完全相同。
:::

## 1.4.7 常见误区

::: warning 误区：循环次数越多，答案越好
不一定。多数任务在第 2–3 轮就收敛了。第 4 轮之后还在转，通常说明工具描述写得不好、
或者错误信息不够可操作，导致模型在原地打转。
:::

::: warning 误区：把整个网页/整个文件塞进上下文就行
塞得进去不等于用得上。长上下文里的中段信息最容易被忽略（业界称为"lost in the middle"）。
正确做法是**先检索、再摘要、只给当前步骤需要的片段**。
:::

## 小结

- 五阶段循环是骨架；真正的工程量在上下文装配与停止条件。
- 成本随轮数近似线性增长，但**累计 prompt** 是叠加的，长任务必须做预算控制。
- 上下文是预算不是草稿纸：写入、选取、压缩、隔离，四招组合用。
