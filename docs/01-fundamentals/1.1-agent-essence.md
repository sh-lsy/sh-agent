# 1.1 什么是智能体：从「一次调用」到「自己决定下一步」

::: tip 一句话结论
智能体 = **模型 + 工具 + 上下文 + 循环**。
它和"调用一次大模型"的唯一本质区别是：**下一步做什么，由模型在运行时决定，而不是你在代码里写死。**
:::

## 1.1.1 两种写法：一个「照剧本演」，一个「临场决定」

同样一个需求——"查一下成都天气，再推荐个景点"，两种写法：

```ts
// A. 普通函数编排：三步顺序由你写死
const weather = await getWeather('成都');            // 第 1 步：你决定
const spots = await getAttraction('成都', weather);  // 第 2 步：你决定
return await summarize(weather, spots);              // 第 3 步：你决定

// B. 智能体：下一步做什么，由模型当场决定
let messages = [{ role: 'user', content: '查一下成都天气，再推荐个景点' }];
while (true) {
  const res = await llm.chat({ messages, tools });
  if (!res.tool_calls) return res.content;
  for (const call of res.tool_calls) {
    messages.push({ role: 'tool', content: await run(call) });
  }
}
```

A 你已经懂了：像照菜谱做菜，第一步炒什么、第二步放什么盐，全写死。

**B 看起来晕，是因为它没有"第几步"，只有一个圈。** 只要把这四行翻译成一句人话，就不难了：

| 代码 | 大白话 |
| :--- | :--- |
| `messages` | 一本**对话记录本**。模型唯一的记忆就是这本本子上的内容 |
| `tools` | 一张**工具菜单**，告诉模型"你能点哪些菜" |
| `while (true)` | **不知道要问几次**，所以一直转，直到它说"够了" |
| `llm.chat({ messages, tools })` | 把本子 + 菜单递过去，问一句"接下来干嘛？" |
| `if (!res.tool_calls) return` | 模型**没点菜**，说明它觉得信息够了，直接给答案 |
| `res.tool_calls` | 模型**点了菜**：要用哪个工具、参数是什么 |
| `await run(call)` | 真正干活的是**你的代码**（模型不执行任何东西） |
| `messages.push({ role: 'tool', ... })` | 把菜端回来，并且**记在本子上**——不记，下一轮它就忘了 |

### 跑一遍就懂了：三轮的实际过程

假设用户问："查一下成都天气，再推荐个景点。"

| 轮次 | 这时本子上有什么 | 模型的决定 | 本子又多了什么 |
| :--- | :--- | :--- | :--- |
| **第 1 轮** | ① 系统提示（含工具菜单）<br>② 用户的问题 | 点 `get_weather(city="成都")` | ③ 点单记录<br>④ 天气结果：局部多云 17.7℃ |
| **第 2 轮** | ①~④ 全部 | 看到"多云"，点 `get_attraction(city="成都", weather="局部多云")` | ⑤ 点单记录<br>⑥ 景点推荐 |
| **第 3 轮** | ①~⑥ 全部 | 信息齐了，**不再点单**，直接写答案 | （循环结束） |

::: tip 一个容易被忽略的真相
模型**每一轮都在重读整本本子**。它并不是"记住了"上一轮，而是你把历史重新递了一遍。
这解释了两件事：为什么上下文越长越贵（1.4 会算这笔账），以及为什么本子上写什么极其重要。
:::

### 遇到意外时，B 为什么能自己拐弯

这是 A 和 B 最关键的区别。用本项目真实会发生的一幕举例：

```text
你问：帮我查一下成都天气
模型第 1 轮：点 get_weather(city="成都市区")     ← 它猜的写法
工具返回：   【查询失败】未找到城市「成都市区」，请换一个更常见的城市名后重试
模型第 2 轮：看到这行错误 → 点 get_weather(city="成都")   ← 自己改对了
工具返回：   成都当前天气：局部多云，17.7℃
```

A 在这种情况下会直接抛错或返回一句死板的兜底文案——因为"城市名可能写错"这个分支，
你根本没写进代码里。而 B 不需要你预先想到这种分支：**错误信息进了本子，模型自己读、自己改。**

::: warning 由此得出一条很实用的工程结论
**工具的错误信息是写给模型看的，不是给你看的。**
`Error: 500` 会让它原地重试；`未找到城市「成都市区」，请换一个更常见的城市名` 才能让它自我修正。
:::

### 再看那三种"意外"

| 场景 | A（写死） | B（Agent） |
| :--- | :--- | :--- |
| 天气接口返回"城市不存在" | 抛错，或返回预设的兜底文案 | 模型读到错误文本，改用"成都"重试 |
| 用户中途补一句"我不想去人多的地方" | 需要改代码、加分支 | 模型把新约束带进下一轮上下文 |
| 需要多查一个"周末是否限行" | 加一步调用 | 模型自己发现信息缺口，追加工具调用 |

::: warning 常见误解
"只要接了 Function Calling 就是 Agent"——不对。如果你在代码里固定了调用顺序（先 A 后 B），
那只是**用模型做了参数抽取**，本质仍是工作流。判断标准只有一条：**控制流在谁手里。**
:::

## 1.1.2 经典四要素，以及为什么在数字环境里要换一套说法

教科书定义（Russell & Norvig 一脉）：

> 智能体是任何能通过**传感器**感知**环境**、并**自主**地通过**执行器**对环境施加**行动**，以达成目标的实体。

## 1.1.3 传统智能体的五级台阶（压缩版）

在 LLM 出现之前，这条演进线走了几十年。它的价值不在于背名词，而在于理解**每一级台阶解决了上一级的什么缺陷**：

| 类型 | 决策依据 | 解决了什么 | 留下的问题 |
| :--- | :--- | :--- | :--- |
| 简单反射 | `if 感知 then 动作` | 快、可预测 | 没有记忆，换个场景就失效 |
| 基于模型 | 内部世界模型（"世界现在是什么样"） | 能推断看不见的状态 | 不知道自己要去哪 |
| 基于目标 | 目标 + 搜索/规划 | 能规划多步路径 | 目标冲突时无法权衡 |
| 基于效用 | 效用函数（"哪种结果更满意"） | 能做取舍 | 效用函数得人来写 |
| 学习型 | 从奖励中更新策略 | 不必预设规则 | 训练成本高、样本效率低 |

**这条线在 2026 年为什么可以略过？**
不是因为它错了，而是因为 LLM 把前四级"吸收"进了同一个东西：世界模型来自预训练，
目标理解来自指令跟随，效用权衡来自对齐训练。你不再需要手写规则库或效用函数——
代价是这个过程变得**不透明、不确定、且按 token 计费**。

## 1.1.4 LLM 驱动的新范式：变的不只是"更聪明"

| 对比维度 | 传统智能体 | LLM 驱动的智能体 |
| :--- | :--- | :--- |
| 核心引擎 | 基于显式编程的逻辑系统 | 基于预训练模型的推理引擎 |
| 知识来源 | 工程师预定义的规则、算法、知识库 | 从海量非结构化数据中学习、内化 |
| 处理指令 | 需结构化、精确的命令 | 可理解高层级、模糊的自然语言 |
| 工作模式 | 确定性的、可预测的 | 概率性的、生成式的 |
| 泛化/适应性 | 弱，局限于预设框架 | 强，具备涌现与泛化能力 |
| 开发范式 | 规则设计、算法编程、知识工程 | 模型训练、提示工程、微调 |

*（原书表 1.1 的完整版见 Hello-Agents；这里改写成可选中、可随主题变色的表格。）*

补三点原书表格里没有、但 2026 年必须知道的差异：

1. **能力的来源变了**：传统智能体的边界由工程师的知识决定；LLM 智能体的边界由**预训练语料 + 上下文**共同决定。这意味着"提示里给什么"和"模型见过什么"同等重要。
2. **失败模式变了**：传统系统是"没覆盖到就崩"，LLM 系统是"**自信地编一个看起来合理的答案**"。后者更难测。
3. **成本结构变了**：传统系统边际成本≈0；LLM 系统**每一步都要付钱**，而且上下文越长越贵。这直接催生了 1.4 要讲的上下文工程。

## 1.1.5 一个具体的对照：旅行助手

原书用"规划一次厦门之旅"举例，2026 年再看这个例子，重点已经不同了：

| 环节 | 2023 年的说法 | 2026 年的现实 |
| :--- | :--- | :--- |
| 规划 | 模型把目标拆成子任务 | 仍然如此，但**推理模型**会把拆解过程显式产出（思维链），这段也要计费 |
| 工具 | 调天气 API、调搜索 | 工具不再写进 prompt，而是由 **MCP 服务器**声明能力清单，运行时动态发现 |
| 动态修正 | 用户说"酒店太贵"→ 重新搜 | 同样成立，但要求 harness 支持**中断与恢复**，而不是把整段历史重发一遍 |

## 1.1.6 Harness：模型外面那层壳，才是你真正在写的东西

这一节值得多花点时间。因为很多人学完 Agent 的默认印象是"我在调模型"，
但真实情况是：**你 80% 的时间在写模型外面那层壳，而那层壳有个名字，叫 harness。**

### 六个部件，每个都直接决定成败

| # | 部件 | 具体做什么 | 没有它会怎样 | 本书在哪讲 |
| :-- | :--- | :--- | :--- | :--- |
| ① | **工具定义与校验** | 名称、用途描述、参数 Schema、执行函数 | 模型瞎编参数，或该调的时候不调 | [1.5](./1.5-first-agent) |
| ② | **上下文装配** | 决定每一轮把什么塞进去：系统提示 / 历史 / 工具结果 / 检索片段 | 越跑越贵，关键信息被稀释 | [1.4](./1.4-agent-loop) |
| ③ | **循环与停止条件** | 最大轮数、预算上限、无进展检测 | 死循环，一晚上烧掉几百块 | [1.4](./1.4-agent-loop) |
| ④ | **权限与沙箱** | 只读/写入分级、危险操作人工确认、文件与网络边界 | 模型把生产库删了 | [1.6](./1.6-protocols-and-boundary) |
| ⑤ | **重试与恢复** | 超时、降级、幂等、断点续跑 | 一次网络抖动让整个任务白跑 | 本章天气工具的主备源 |
| ⑥ | **观测与评估** | 轨迹记录、token 计量、成功率与失败样本 | 出问题完全无法复盘 | 第四部分 |

### 同一个模型，两个 harness，结果能差很远

这不是理论。下面三件事都不换模型，只改壳：

| 改什么 | 不改 | 改了 |
| :--- | :--- | :--- |
| **工具描述** | `"查询天气"` | `"查询指定城市的当前实时天气。用户问穿衣、出行、是否带伞时使用"` |
| **错误信息** | `Error: 500` | `未找到城市「成都市区」，请换一个更常见的城市名重试` |
| **上下文策略** | 每轮把全部历史原样塞进去 | 只保留最近 3 轮 + 一份结构化任务状态 |

结果差异分别是：**该调不调 / 原地重试到死 / 第 8 轮开始"失忆"** 与 **按需调用 / 一次自我修正 / 长任务稳定跑完**。

::: tip 为什么行业里说「模型是耗材，harness 是资产」
- 换模型通常只是改一行配置（`.env` 里的 model 名）；
- 而工具描述改好一次、失败兜底加一个、上下文裁剪做对一次，**所有任务都跟着受益**，且换模型后依然有效。

所以"我们的 Agent 效果不好"这句话，先别急着怪模型，按 ①→⑥ 挨个查一遍，
八成能在里面找到原因。这也是本章后面每一节的实际落点。
:::

## 1.1.7 三个高频误区

::: warning 误区 1：Agent 一定比工作流高级
错。固定流程能解决的问题，用 Agent 只会更慢、更贵、更难测。
正确顺序是：**先写工作流，只有当"下一步取决于上一步的结果、且分支无法穷举"时才引入循环。**
:::

::: warning 误区 2：Agent 就是"多轮聊天"
聊天是**人驱动**的轮次；Agent 是**模型驱动**的轮次。聊天里停下等你说下一句，
Agent 里是它自己决定"还要不要再查一次"。
:::

::: warning 误区 3：接了工具就等于有了行动力
工具的真正难点不在调用，而在**返回值**：格式是否稳定、错误是否可读、内容是否可信。
一个返回 `Error: failed` 的工具会让模型反复重试；返回 `权限不足，需要先执行 chmod +x` 的工具能让它自我修正。
:::

## 小结

- Agent 的本质是**控制权转移**：从"你写死流程"变成"模型在运行时选动作"。
- 四要素在工程上的对应物是 Model / Tools / Context / Loop，四者加上权限与观测 = **Harness**。
- 传统五类智能体是一条"逐步补能力"的演进线，LLM 把它们合并了，但代价是不透明与按量计费。

下一节我们把"分类"这件事讲清楚：为什么同一个模型，有时该让它立刻回答，有时该让它想很久。
