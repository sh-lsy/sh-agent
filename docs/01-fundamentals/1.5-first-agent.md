# 1.5 手写第一个智能体：从正则解析到函数调用

::: tip 一句话结论
2024 年写 Agent 要"教模型按格式输出，再用正则抠出来"；
2026 年模型原生就会返回结构化的 `tool_calls`，**你只需要定义工具、校验参数、执行、回灌。**
:::

## 1.5.1 先看被淘汰的写法（原书 1.3 的方案）

Hello-Agents 原书为了降低依赖门槛，用纯文本协议驱动：

```text
系统提示：
你可以使用以下工具：
  get_weather(city: str)
输出格式要求：
  Thought: 你的思考
  Action: 工具名(参数)

模型输出：
  Thought: 用户想知道北京天气，我需要调用天气查询工具
  Action: get_weather("北京")

你的代码：
  const m = output.match(/Action:\s*(\w+)\((.*?)\)/);   // ← 全部脆弱性都在这
```

这段正则在真实使用中会遇到：

- 模型输出 `Action: get_weather(city="北京")` → 解析出 `city="北京"`，你还得再去引号
- 模型输出 Markdown 代码块包着的 Action → 正则匹配不到
- 模型输出中文括号 `get_weather（"北京"）` → 直接崩
- 模型一次想调两个工具 → 这套协议只支持单动作

::: warning 为什么必须在 2026 年放弃它
不是"不够优雅"，而是**错误率不可控**。这类解析失败会以"Agent 忽然不工作了"的形式出现，
而且极难复现——因为同样的输入，模型下次可能换个写法。
:::

## 1.5.2 现在的写法：让模型返回结构化意图

同样一件事，现代协议是这样的：

```ts
const res = await client.chat.completions.create({
  model,
  messages,
  tools: openAITools,     // ← 工具以 JSON Schema 声明
  tool_choice: 'auto',
});

// 模型返回的是结构化对象，不是自然语言
res.choices[0].message.tool_calls;
// [{ id: 'call_1', function: { name: 'get_weather', arguments: '{"city":"成都"}' } }]
```

你不再"解析文本"，而是**读字段**。参数是 JSON 字符串，用 `JSON.parse` + Zod 双重校验。
这就是本项目 `first-agent.ts` 的做法。

## 1.5.3 三个步骤，逐段看代码

### 第一步：用 Zod 定义工具（单一真理源）

```ts
export const weatherTool: AgentTool = {
  name: 'get_weather',
  description: '查询指定城市的当前实时天气与温度情况',   // ← 模型靠这句话决定要不要用
  schema: z.object({
    city: z.string().describe('需要查询天气的城市名称，例如 "成都"、"北京" 或 "上海"'),
  }),
  execute: async ({ city }) => {
    // 真实实现里带 3.5s 超时与兜底，见 learning/01-fundamentals/src/first-agent.ts
    return `${city}当前天气：阴，气温 17℃`;
  },
};
```

::: tip 工具描述是写给模型看的，不是写给人看的
- `description` 要说明**什么时候用**，而不是"这个函数做什么"
- 参数 `.describe()` 要**给例子**（`例如 "成都"`），模型对例子最敏感
- 返回值要**结构化且可操作**：`权限不足，请先执行 chmod +x` 比 `Error: failed` 有用得多
:::

### 第二步：把 Zod 转成模型认识的 JSON Schema

```ts
export function formatOpenAITools(tools: AgentTool[]): ChatCompletionTool[] {
  return tools.map((t) => {
    const jsonSchema = zodToJsonSchema(t.schema) as any;
    delete jsonSchema.$schema;                 // OpenAI 不需要这个字段
    return { type: 'function', function: { name: t.name, description: t.description, parameters: jsonSchema } };
  });
}
```

一份 Zod 定义，同时得到：**编译期类型**、**运行时校验**、**给模型的 schema**。三者不会漂移。

### 第三步：循环本体（约 40 行）

```ts
for (let round = 1; round <= maxIterations; round++) {
  const res = await client.chat.completions.create({ model, messages, tools, tool_choice: 'auto' });
  const msg = res.choices[0].message;

  // ① 思维链（推理模型才有），单独作为一种事件
  if (msg.reasoning_content) yield { type: 'reasoning', content: msg.reasoning_content, round };

  // ② 可见回答，可能为空
  if (msg.content) yield { type: 'thought', content: msg.content, round };

  // ③ 真实 token 计量
  if (res.usage) yield { type: 'usage', ...res.usage, round };

  // ④ 没有工具调用 = 收敛
  if (!msg.tool_calls?.length) return yield { type: 'final_answer', content: msg.content, round };

  messages.push(msg);                          // 把「调用意图」记进历史

  for (const call of msg.tool_calls) {
    const tool = toolMap.get(call.function.name);
    let output: string;

    try {
      const args = tool.schema.parse(JSON.parse(call.function.arguments));  // 双重校验
      output = await tool.execute(args);
    } catch (err) {
      // 关键：错误不抛出，而是变成 Observation 让模型自己修
      output = `【工具执行异常】${(err as Error).message}；请调整参数后重试。`;
    }

    yield { type: 'tool_result', tool: call.function.name, output, round };
    messages.push({ role: 'tool', tool_call_id: call.id, content: output });
  }
}
```

::: warning 最容易被忽略的一行
`messages.push(msg)` 必须在执行工具**之前**。
模型的 `tool_calls` 和工具的 `role: 'tool'` 回复是一一配对的，顺序错了 API 会直接报错。
:::

## 1.5.4 防御性执行：让错误变成模型的信息

原书把工具调用包在 `try/except` 里然后 `print` 错误。现代写法**不是打印，而是回灌**：

| 做法 | 结果 |
| :--- | :--- |
| 抛异常崩进程 | 用户看到白屏 |
| 捕获后打印、返回空字符串 | 模型不知道发生了什么，继续瞎猜 |
| **捕获后格式化成可读文本回灌** | 模型读到"缺少参数 city"，下一轮补上 |

这也是"自我修正"能力的来源——它不是模型变聪明了，而是**你把错误信息喂给它了**。

```text
   📤 结果: 成都当前天气：局部多云，气温 17.7℃，体感 16.9℃，湿度 58%，风速 4.1km/h（数据来源：Open-Meteo，观测时间：16:00）
🪙 [Usage] 本轮 578 tokens（prompt 486 / completion 92），会话累计 578

──────── 第 2 轮循环 ────────
💭 [Reasoning 思维链]: 现在多云、17.7℃，适合户外，优先推荐开阔景点……

```

注意三个细节：

1. 第 2 轮才出现 `reasoning`——因为第 1 轮模型直接说话了，没有额外汇总；
2. 工具返回里带**数据来源**，避免把兜底数据当实时数据；
3. `usage` 是**接口返回的真实值**，不是估算。

## 1.5.6 三个典型失败，以及怎么修

| 现象 | 根因 | 修法 |
| :--- | :--- | :--- |
| 模型反复调同一个工具、参数一模一样 | 返回值没有新增信息，或错误信息不可读 | 返回值里加"已查到/未查到"的明确信号；错误信息给可执行建议 |
| 参数缺字段 / 类型错 | schema 太宽松，或描述里没给例子 | `.describe()` 加示例；用 Zod `.min()`/`.enum()` 收紧 |
| 转到第 6 轮还没结论 | 没有停止条件，或任务本身需要工作流 | 加预算上限；判断是否该改写成固定流程（见 1.6） |

## 1.5.7 练习

1. 给旅行助手加第三个工具 `get_visa_policy(country)`，要求：参数用 Zod 枚举，返回值包含"是否需要提前办理"。
2. 故意让 `get_weather` 在收到空字符串时抛错，观察模型能否在下一轮修正参数。
3. 把 `maxIterations` 改成 1，看输出会变成什么样——理解"收敛"依赖多次循环。

## 小结

- 文本协议 + 正则已经过时，**结构化 `tool_calls` + Schema 校验**是现在的基线。
- 工具设计的三条铁律：描述写用途、参数给例子、错误给建议。
- 错误要**回灌**而不是抛出，这才是 Agent 自愈的来源。
